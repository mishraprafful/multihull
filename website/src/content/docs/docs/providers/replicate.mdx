---
title: Replicate
description: Cog models on Replicate deployments, routed as Cog predictions.
---

Replicate runs Cog models only, so a service with a Replicate target sets `build.target: cog` and every target runs the same Cog image. `apply` calls Replicate's HTTP API (`https://api.replicate.com/v1`) and the Cog CLI: it creates the private model `<account>/multihull-<svc>` if missing, runs `cog push r8.im/<account>/multihull-<svc>` in `build.context`, then creates or updates the deployment `multihull-<svc>-<provider>` with the pushed version. On `main`, unreleased: tested against a mocked API, not yet run against Replicate.

```yaml
container:
  build: {context: ., target: cog}
  port: 5000
  health: {path: /health-check}

targets:
  - provider: replicate
    type: replicate
    priority: 2
```

Credentials: `REPLICATE_API_TOKEN`, sent as `Authorization: Bearer`. `hull doctor` reads the token's account and fails on 401 or when `cog` is not on `PATH`. `cog push` needs a Cog login: set `REPLICATE_CLI_AUTH_TOKEN` (from replicate.com/auth/token) and `apply` runs `cog login --token-stdin` with it, or run `cog login` once yourself. `replicate.owner` is optional; when set it must be the token's account, since Replicate creates models and deployments only there.

## Routing

Replicate has no HTTP passthrough: a deployment answers `POST /v1/deployments/<owner>/<name>/predictions` with a Cog prediction body. The endpoint in the snapshot is the deployment URL, so a client calling `POST /predictions` with `{"input": {...}}` reaches the predictions URL on Replicate and the Cog server's own `/predictions` on every other target. Routes for Cog services use `protocol: http`; an OpenAI-compatible request has no Replicate equivalent.

The router injects `Authorization: Bearer` and `Prefer: wait=60` on traffic and probes. `Prefer: wait` makes Replicate hold the response until the prediction finishes, like a Cog server does; a prediction still running after 60 s comes back with status `starting` or `processing` and no output, and its polling URL is on Replicate, not the router. Keep predictions under 60 s or call Replicate directly for long ones. The route's `timeouts.first_byte` must exceed the prediction time on every target.

The router probes the deployment URL itself (`GET`), not `container.health.path`, because Replicate does not expose the container. A 2xx means the deployment exists and the token works; it says nothing about instances.

## Lifecycle

- `apply` hashes `build.context` (ignoring `.git`, `.cog` and `__pycache__`) and pushes only when the hash or the model changed since the state's ref. It then sends one `PATCH` with the fields that differ from the deployment's current release (version, hardware, instances), or nothing; every `PATCH` creates a new release. With no state, `apply` pushes and adopts the deployment by name.
- `apply` fails before any call when `container.env` or `container.secrets` is set (the deployments API takes no environment; build configuration into the image), when `scaling.replicas` exceeds Replicate's limits (`min_instances` 5, `max_instances` 20), or when no GPU class maps to hardware. It checks the chosen hardware against `GET /v1/hardware` before pushing.
- `hull deploy --wait` and `hull status` report Ready once the deployment's current release runs the applied version with `min_instances` of at least 1. Replicate's API reports no instance state, so the first predictions may wait for an instance to boot.
- `scale` patches `min_instances` and `max_instances`; values above the limits, a 400 or a 422 are permanent refusals.
- `hull logs` prints nothing: Replicate has logs per prediction, not per deployment.
- `destroy` sets `min_instances` and `max_instances` to 0, then deletes the deployment. Replicate deletes only deployments offline and unused for 15 minutes, so the first `destroy` usually fails with that reason and keeps the state record; run it again later. A 404 counts as gone. The model and its versions stay, like images in a registry.

## Translation

| Spec field | Replicate |
|---|---|
| `container.build` | `cog push r8.im/<account>/multihull-<svc>` in `build.context`; model created private |
| `container.command`, `port` | ignored; the Cog image serves its predictor (port 5000 on other targets) |
| `resources.gpu` | deployment `hardware`, first class Replicate offers: L4 to `gpu-l40s`, A10G to `gpu-a40-small`, A100-40 and A100-80 to `gpu-a100-large`, H100 to `gpu-h100`; `cpu` when empty |
| `scaling.replicas` | `min_instances`, `max_instances` |
| `scaling.concurrency` | not applicable |
| `container.health` | not sent; the router probes the deployment URL |
| `container.env`, `secrets` | refused |
| endpoint | `https://api.replicate.com/v1/deployments/<owner>/<name>`, plus `Authorization: Bearer` and `Prefer: wait=60` injected by the router |

Ref stored in state: owner, model, deployment name, pushed version and the build context hash. Fallbacks stay warm because `fallbackScaleToZero` defaults to `false`, so `min_instances` is never 0 unless you opt in.

Example: [`examples/replicate-echo`](https://github.com/mishraprafful/multihull/tree/main/examples/replicate-echo), a Cog echo model on Docker and Replicate.
