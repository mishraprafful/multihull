# 2026-10-26 Baseten translator (issue 64)

- Branch `feat/baseten-provider`, PR 177. No Baseten credential was available: everything is tested against `python/tests/fake_baseten.py` (an `httpx.MockTransport` that checks the documented request fields, the S3 SigV4 header and the archive), never against Baseten.
- API choice: the management API documents the whole push for a config-only Truss (`examples/create-a-model-with-rest`): `POST /v1/prepare_model_upload`, upload with the returned STS credentials, `POST /v1/models` or `/v1/models/{id}/deployments` with `environment_name` and `autoscaling_settings`. The `truss` library was rejected: it pins `rich<14`, pulls boto3 and google-cloud-storage, and pushes over GraphQL. The SigV4 PUT matched botocore's `S3SigV4Auth` signature for virtual-hosted and path-style buckets.
- Review fixes: a failed rollout while the previous deployment serves is Degraded, not Failed, so the router keeps a working fallback; a model found by name is adopted or deleted only when unique in the organization (names are unique per team only) and labelled for this service and provider; S3 errors report only `<Code>`; identifier secret names are exported instead of passed through `env` argv; `%` in the command is refused because supervisord.conf interpolates it.
- Truss configs rendered for a GPU and a CPU spec pass `TrussConfig.from_dict(...).validate_forbid_extra()` in truss 0.18.34.
- Unknowns for the first live run: S3 key layout and bucket naming of the issued upload target, whether `DELETE /v1/models/{id}` succeeds while a production deployment is active, whether environment-level autoscaling reaches the serving deployment (the only `PATCH` sent, after review), whether the mock image's `/app/.venv` survives Baseten's build (it reserves `/app`), and Baseten's own error statuses for an `edge_error` signature.
